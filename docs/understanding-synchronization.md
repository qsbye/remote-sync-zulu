# Understanding Synchronization

> 本文介绍了 Syncthing 用于同步文件的底层机制（高层面概述）。
>
> 原文：<https://docs.syncthing.net/users/syncing.html>（版本：v2.1.0）

## Blocks（数据块）

文件被划分为若干 *块（block）*。构成同一文件的所有块大小相同（文件中最后一个块可能较小）。块大小取决于文件大小，范围从 **128 KiB 到 16 MiB**。每个文件被切分为多个这样的块，并计算每个块的 **SHA256 哈希**，最终生成一个 *块列表（block list）*，包含该文件所有块的偏移量、大小和哈希值。

要更新某个文件时，Syncthing 会将文件当前版本的块列表与目标版本的块列表进行对比，然后为每个有差异的块寻找来源。来源可能有两种：

- **本地**：如果另一个文件已包含相同哈希的块，则直接在磁盘上复制该块；
- **集群中的其他设备**：通过网络从其他设备请求该块。

当块从其他设备复制或接收过来时，会计算其 SHA256 哈希并与预期值比对：

- 匹配 → 写入文件的临时副本；
- 不匹配 → 丢弃，并尝试寻找该块的其他来源。

## Scanning（扫描）

Syncthing 通过两种方式检测变更：

1. **定期全量扫描**；
2. **文件系统通知（"watcher"）**。

默认情况下 watcher 处于启用状态，全量扫描每小时执行一次，此行为可按文件夹调整。增大全量扫描间隔可以降低资源占用，适用于变化不频繁的大型文件夹。为避免所有文件夹在同一时刻重新扫描，实际扫描间隔为设定值的 **3/4 到 5/4 之间的随机时间**。即使启用了 watcher，也建议保留定期全量扫描，因为某些变更可能无法被 watcher 捕获。

在重新扫描期间（无论是全量还是 watcher 触发），会检查现有文件的以下属性是否发生变化：

- 修改时间（modification time）
- 大小（size）
- 权限位（permission bits）

若基于这些属性检测到变更，文件将被"重新哈希"——即为该文件计算新的块列表。不读取文件并为每个块重新计算 SHA256 哈希，就无法得知文件的哪些部分发生了变化。

watcher 检测到变更后**不会立即**安排扫描：

- 变更会累积 **10 秒**（可通过 [`fsWatcherDelayS`](https://docs.syncthing.net/users/config.html#config-option-folder.fswatcherdelays) 调整）；
- 被删除的文件会额外延迟 **1 分钟**。

因此，从做出变更到变更出现在另一台设备上，存在轻微延迟是正常现象。

每次重新扫描后，检测到并已哈希的变更会被传输到其他设备。

## Syncing（同步）

Syncthing 会为每个文件跟踪多个版本：

- **本地版本（local version）**：当前磁盘上的版本；
- **其他所有已连接设备通告的版本**；
- **全局版本（global version）**：即"最佳"版本（通常是最近的版本），也是每台设备努力同步至的目标版本。

这些信息保存在 *索引数据库（index database）* 中，数据库位于配置或数据目录下，名为 `index-*`（星号处为某个版本号）。

当收到来自其他设备的新索引数据时，Syncthing 会重新计算每个文件的全局版本，并将其与当前本地版本进行比较。当两者不同时，Syncthing 需要同步该文件：比较块列表以构建所需块的清单，然后按照上文所述，从网络请求或在本地复制这些块。

## Conflicting Changes（冲突变更）

Syncthing 能够识别冲突。当同一文件在两台设备上被同时修改且内容确实不同时，其中一个文件将被重命名为：

```
<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>
```

冲突解决规则：

1. **修改时间较旧**的文件会被标记为冲突文件并被重命名；
2. 若修改时间**相同**，则来自设备 ID 前 63 位数值较大的设备的文件被标记为冲突文件；
3. 若冲突发生在**修改与删除**之间，且删除一方在冲突解决中胜出，则文件仍会被按上述方式重命名为冲突副本。

> **注意**：`<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>` 文件在创建后会被当作普通文件处理，因此它们会在设备之间传播。这样做的原因是：冲突在某一台设备上被检测并解决，从而创建了 `sync-conflict` 文件，但在其他所有设备上这同样是一个冲突，而且我们无法知道从用户角度来看哪个冲突文件才是"最佳"的。

## Case Sensitivity in File Names（文件名大小写敏感性）

原则上，Syncthing 使用 *大小写敏感* 的路径，即 `file.txt` 和 `FILE.txt` 表示两个独立的事物。因此，它绝不会将两者视为相关联的文件来同步其内容。然而某些操作系统（如 Windows、Mac，以及某种程度上的 Android）则相反，将它们视为同一个文件（或目录），且永远不能同时拥有这两个名称。

因此：

- 如果远程设备共享的文件与本地现有文件发生大小写冲突，该文件将无法同步到此类系统，并会被 Syncthing 报告为 **case conflict（大小写冲突）**；
- 类似地，如果两台远程设备向你的本地设备共享了大小写不同的变体，只有其中一个会被拉取，另一个会被标记相应的错误信息。目前哪个会"胜出"是**不可预测的**。

要解决这种大小写冲突，你需要确定一个统一的文件名，并在所有相关的大小写不敏感设备上**手动**强制执行。

> 这种谨慎行为是为了避免因不同文件互相覆盖内容而造成数据丢失。在 1.9.0 版本之前，同一文件可能会在两个大小写不同的文件名下被错误地访问。

以上所述均不涉及文件夹根路径，仅涉及每个共享文件夹内的相对路径。

## Temporary Files（临时文件）

Syncthing **从不直接写入**目标文件。所有变更都先写入一个临时副本，然后再移动覆盖旧版本。如果在复制或同步过程中发生错误（例如某个必需的块不可用），临时文件会保留最多 **一天**，以避免无谓地从网络重复请求数据。

临时文件命名规则：

| 系统 | 常规命名 | 文件名过长时 |
|------|---------|-------------|
| Linux / macOS 等 | `.syncthing.original-filename.ext.tmp` | `.syncthing.<hash>.tmp` |
| Windows | `~syncthing~original-filename.ext.tmp` | `~syncthing~<hash>.tmp` |

其中 `original-filename.ext` 为目标文件名，`<hash>` 为原始文件名的 SHA-256 哈希。临时文件通常是隐藏的。

> **Note**
>
> 前缀 `.syncthing.` 和 `~syncthing~` 属于 Syncthing 的命名空间：任何以它们开头的文件都会被自动忽略并排除在同步之外。请避免在你自己的文件名中使用这些前缀。
